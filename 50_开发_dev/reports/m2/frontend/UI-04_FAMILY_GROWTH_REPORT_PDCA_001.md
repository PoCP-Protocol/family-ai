# UI-04 家庭成长报告 PDCA 001

> **本轮范围**：承接 UI-03 的“生成个性化方案”入口，为 UI-04 建立家庭成长报告读取投影，并将其显式衔接到 UI-05 的 90 天成长计划预览。该轮只处理“理解当前关注方向 → 查看报告 → 查看计划”的家庭内闭环；不创建诊断、总分、排名、教育效果结论、订单、预约、通知、分享或任何外部效果。

## 1. Plan：研究与产品设计

UI-04 基线是移动端“AI成长诊断”页面，保留的可见骨架包括家庭信息蓝卡、五维可视化区、核心关注问题、三条成长建议和“生成个性化方案”底部 CTA。其既有可视化数值不应被解释或替换为家庭总分、儿童诊断、同龄比较或教育效果；本轮仅在基线容器下方增加一个轻量、可读的成长报告摘要，并保留原 CTA 的触点位置。

本轮将“报告”定义为**围绕家长已选关注方向的参考内容**，而不是对儿童或家庭的判断。行动计划研究指出，目标本身通常不足以推动行动；更可执行的计划应说明何时、何地及如何开始，并以短周期复盘调整。[1] 同时，家庭共同目标设计应从家庭自身的优势、优先事项、沟通、目标设定、后续跟进和回顾中逐步形成，而不是由系统替家庭作决定。[2]

因此，报告页的可见内容采用积极、可练习、可调整的表达：一项当前关注方向、一个本周小行动、一个可能的困难及替代做法、以及进入 90 天计划的下一步入口。所有内容都是测试环境中的规则化示例；该事实留在内部数据与文档，前台仅显示面向家庭的自然语言。

| 设计问题 | 本轮答案 | 不做的事 |
|---|---|---|
| 报告来源 | 读取 UI-02 最近一次关注方向及 UI-03 已查看记录；缺省时使用“亲子沟通”示例方向 | 不从自由文本模型生成或写入核心对象 |
| 报告结构 | `focus`、`headline`、`three observations`、`this-week action`、`fallback action`、`plan preview` | 不输出分数、排名、因果结论或诊断 |
| 计划结构 | UI-05 接收四阶段预览：看见、调整、共创、稳定 | 不创建正式 `GrowthPlan`、`GrowthTask`、`Intervention` |
| 状态迁移 | UI-03 查看说明 → UI-04 阅读报告 → UI-04 查看计划 → UI-05 预览计划 | 不把“查看”当作家庭同意、正式决定或行动完成 |
| 用户文案 | “你当前更关注”“可以从这里开始”“本周小行动”“查看 90 天成长计划” | 不显示工程状态、审核、测试数据或内部命令 |

## 2. Do：实现契约

本轮新增的共享投影字段为 `report_draft` 与 `plan_preview`。二者位于 Core Growth 的 UI-04/UI-05 卡片内，并由 API 外观根据当前家庭的最近 UI-02 选择和 UI-03 查看记录补全。字段只读；相关的流程事件沿用现有家族范围、角色校验、幂等键和审计轨迹。

报告到计划的 CTA 写入 `PREVIEW_SYNTHETIC_90_DAY_PLAN_DRAFT` 流程事件，随后重新读取同一家庭投影并进入 UI-05。该事件表示页面流程已发生，不代表计划被确认、任务被指派或成长产生效果。前台按钮为“查看 90 天成长计划”，而非内部事件名称。

## 3. Check：测试与视觉验收

自动化验收至少覆盖以下路径：UI-02 选择关注方向；UI-03 进入成长说明；UI-04 显示相同关注方向和规则化报告摘要；UI-04 CTA 记录幂等流程事件；UI-05 显示同一方向的阶段计划预览；跨家庭角色请求失败；未知或未选方向回落到中性示例。前端测试额外检查 UI 可见文本不包含 `DEV`、`synthetic`、`NOOP`、`Model Gateway`、`审核` 或 `回执`。

视觉验收使用原有 UI-04 纵向基线。动态内容必须位于基线图外的可读区，不覆盖家庭信息、雷达图、三条建议或底部 CTA 的视觉结构；移动视口内须能清晰看到报告摘要与计划入口。

## 4. Act：本轮完成后的处理

本轮若通过测试和视觉复核，将文档、契约、服务、控制器、前端与测试一起进行限定提交并推送 GitHub。推送确认后，下一轮才进入 UI-05 的“计划预览 → 本周任务”纵切；若本轮失败，先修复并重复本轮，不提前扩展到其它 UI。

最终刷新后视觉复核通过：UI-04 原始截图基线完整保留；报告摘要在基线后自然呈现；页面仅保留一个“查看 90 天成长计划”后续入口，不再出现重复的通用成长操作卡。用户可读内容只包含当前关注、可尝试做法、本周小行动与替代做法，未出现开发过程术语。
