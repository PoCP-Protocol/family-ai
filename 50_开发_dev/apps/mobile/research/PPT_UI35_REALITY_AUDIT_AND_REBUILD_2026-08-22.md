# Family Growth AI Platform：PPT × 35 UI 真实性审计与重构基线

**审计日期：** 2026-08-22
**范围：** 三份 PPT、UI-01 至 UI-35、Expo App、Web 家庭门户、现有 NestJS Family API、Test PostgreSQL 与运营回执模型。
**结论口径：** 页面被渲染、可跳转或显示合成卡片，均**不等于功能完成**。本审计仅将同一家庭范围的读模型、受控命令、持久化草稿、可回读状态或清晰的失败/空态算作真实实现证据。

## 1. 先承认差距

用户的判断成立。现有平台已经有一部分真实地基：家庭范围认证、Journey Plan、今日任务 check-in、商品意向、预约请求、服务记录、会员资产、运营回执与 Family Case/SLA 都存在于同一 Family API 和 PostgreSQL 模型中。但是，移动首页仍使用固定任务与固定推荐图；不少 UI 依赖 Dev 合成投影、局部本地草稿或只读展示；Web 默认门户更是以视觉状态机为主体，只有显式 Dev/Test 会话才接入若干投影。它们不能被表述为三份 PPT 和 35 UI 所要求的完整家庭成长平台。

> **重构准则：** 每个 UI 都必须回答四个问题：它读取哪个家庭范围对象？用户的操作改变哪个受控对象？家庭、App、Web、运营台如何回读同一状态？没有数据、无授权或操作失败时向家长显示什么？

## 2. PPT 的产品主线不能被拆成孤立页面

三份 PPT 共同要求的不是一套页面集合，而是一条家庭关系旅程：**现实困扰进入 → 家庭理解 → 小行动 → 21/90 天陪伴 → 内容/专家/活动支持 → 会员权益与家庭资产 → 成长记录与自愿传播**。榜样教育材料中的“孩子问题是入口、父母成长是价值、家庭改变是结果”是产品叙事，不是儿童诊断或效果证明。家庭支持的外部设计输入同样强调给照护者提供可执行的支持和安全、积极的家庭环境，而不是以单次记录宣称孩子结果。[1]

| 循环 | PPT/35 UI 应呈现的场景 | 当前真实基础 | 当前主要断点 |
|---|---|---|---|
| 家庭入口与理解 | 首页困扰入口、家庭测评、解读、下一步 | UI-02/03 有 onboarding、解读、审核干预与同意读取 | UI-01 今日任务/推荐仍主要固定；测评不是完整问题→答案→证据链 |
| 21/90 天行动 | 挑战营、计划、每日任务、回顾 | Journey Plan 创建/确认/阶段回顾、UI-09 check-in | 首页和计划摘要未统一读取同一行动投影；营与计划的关系未显式汇总 |
| 内容与孩子参与 | 孩子练习、故事、课程、工具 | 受控本地选择/私有故事、部分 Dev 平台投影 | 多数内容没有真实内容版本、完成进度、家庭可见回读 |
| 商业权益 | 商城、详情、意向、邀请、拼团、会员 | 商品目录、意向、权益、会员资产、运营回执 | 邀请/拼团/积分多为私有草稿或页面表现，缺少同源家庭资产解释和 Case 状态 |
| 专家与活动服务 | 直播、顾问、咨询、活动、服务记录 | 服务供给、预约请求、服务记录、运营 Case | 服务需求→家庭可见状态→下一步承接未统一；直播/活动多停在入口或只读卡 |
| 社区与成果账户 | 家长交流、打卡、成果、档案、会员中心 | 私有小记、受控社区草稿、资产/服务投影 | 公开互动、分享、排行榜不应开启；家庭私有记录与会员资产没有统一账户投影 |

## 3. UI-01 至 UI-35 当前真实性分层

| UI | 主要场景 | 当前结论 | 已有真实证据 | 必须补齐的核心能力 |
|---|---|---|---|---|
| UI-01 | 家庭首页 | **PARTIAL** | 路由、本地今日行动状态、下拉刷新外壳 | 聚合今日行动、计划阶段、已审核路径、服务/权益、Case 下一步的同源首页投影 |
| UI-02 | 家庭测评 | **PARTIAL** | 成长关注选择、onboarding/Dev 流程记录 | 完整问题集、答案版本、提交回执、可追溯测评输入 |
| UI-03 | 成长解读 | **REAL-CORE** | 报告解读、审核干预库、Consent/Context | 将“为什么推荐/适用范围/交付物/下一步”作为同源投影而非局部文案 |
| UI-04 | 90 天计划 | **REAL-CORE** | 计划预览、优先项、创建/确认、阶段回读 | 计划、营、今日行动和服务建议的统一阶段投影 |
| UI-05 | 陪跑服务 | **PARTIAL** | 服务旅程、阶段回顾、任务/社区/专家路由 | 陪跑过程、家庭可见服务状态与可执行下一步统一回读 |
| UI-06 | 我的/会员入口 | **PARTIAL** | 服务旅程、私有打卡草稿、账户路由 | 同源会员/权益/订单/Case 汇总，而不是局部计数 |
| UI-07 | 孩子成长助手 | **SHELL** | 跳回测评 | 家长授权下的家庭练习、完成记录与儿童友好呈现；不建独立儿童画像/账户 |
| UI-08 | 阶段回顾 | **PARTIAL** | 家庭回顾 readback、计划/任务路由 | 真实行动、观察（Perspective）、服务/内容触发的可解释回顾 |
| UI-09 | 今日任务 | **REAL-CORE** | 今日行动、check-in、干预库、Context Resolver | 首页/计划/营与同一行动 ID、状态和下一步完全汇聚 |
| UI-10 | 孩子任务/能量 | **PARTIAL** | Dev Core Growth 投影 | 移除只为展示的能量数；改为家长同意下的练习参与与家庭观察 |
| UI-11 | 成长广场/入口 | **PARTIAL** | Dev Platform Surfaces、路由 | 将内容、活动、家庭私有记录改由内容/服务投影提供 |
| UI-12 | 成长故事 | **PARTIAL** | 私有故事草稿、部分投影 | 草稿→家长确认→家庭档案回读；不得默认公开或当作成果证据 |
| UI-13 | 商城首页 | **PARTIAL** | 商品目录投影、详情路由 | 目录需要适用范围、交付物、权益、当前家庭状态与推荐理由 |
| UI-14 | 商品详情/方案意向 | **REAL-CORE** | 商品/客户投影、意向提交、权益回执 | 家庭可见的意向 Case、下一步、运营响应状态 |
| UI-15 | 邀请有礼 | **PARTIAL** | 私有邀请草稿、Dev 事件 | 不发送外部邀请；改为邀请草稿、分享许可与可审计状态 |
| UI-16 | 拼团 | **PARTIAL** | 私有拼团草稿、Dev 事件 | 不占名额/不收款；明确显示家庭意向与人工确认状态 |
| UI-17 | 积分任务 | **PARTIAL** | 会员客户投影、受控本地回执 | 积分规则、账本、兑换资格需先作为同源权益规则和家庭资产回读 |
| UI-18 | 会员中心 | **PARTIAL** | 会员计划、会员/商业资产投影 | 与 UI-06 合并为同一账户投影，避免两个会员中心不同数据 |
| UI-19 | 专家服务入口 | **PARTIAL** | 服务供给、直播/咨询入口 | 目录卡的适用范围、交付物、预约意向和家庭 Case 状态 |
| UI-20 | 服务详情 | **PARTIAL** | 服务供给读取 | 统一价值说明、家长确认、服务前准备与后续记录 |
| UI-21 | 在线咨询需求 | **REAL-CORE** | 预约请求、服务记录、运营回执 | 家庭可见 Case 状态和下一步，不展示内部负责人/SLA |
| UI-22 | 活动列表 | **PARTIAL** | 活动目录读取 | 活动意向、资格/名额仅受控草稿，且可回读家庭状态 |
| UI-23 | 活动详情/兴趣 | **PARTIAL** | 兴趣草稿、运营事件 | 兴趣→Family Case→家庭下一步的可见状态 |
| UI-24 | 我的服务记录 | **PARTIAL** | 服务客户投影、取消命令、路由 | 预约、服务记录、活动兴趣和 Case 的单一家庭服务时间线 |
| UI-25 | 家长社区 | **PARTIAL** | 社区只读投影、路由 | 家庭私有草稿、审核发布申请和状态；不启用跨家庭排名/默认公开 |
| UI-26 | 发布/小记 | **PARTIAL** | 私有社区草稿、AI 标签草稿 | 草稿保存/失败/确认状态与家庭档案回读，AI 标签为建议而非事实 |
| UI-27 | 动态详情 | **PARTIAL** | 互动草稿 | 互动意图需明确为本地/待审核，避免假称已发布/已点赞 |
| UI-28 | 社区成果 | **PARTIAL** | 社区投影、路由 | 仅聚合家庭允许展示的记录；不做家庭榜单和儿童比较 |
| UI-29 | 家庭成果 | **PARTIAL** | 资产/成果投影 | 记录来源、可见范围、非因果结果边界和家庭可见资产时间线 |
| UI-30 | 积分/邀请/续费 | **PARTIAL** | 会员、商品和资产投影 | 统一积分/权益账本、邀请草稿、续费意向与运营 Case |
| UI-31 | 服务资产 | **PARTIAL** | 服务客户投影 | 面向家庭的服务承接状态、下一个动作、记录回读 |
| UI-32 | 订单与权益 | **PARTIAL** | 商业客户投影 | 将意向、权益、到期、服务交付、Case 关联为同源资产时间线 |
| UI-33 | 成长档案 | **SHELL** | 仅路由入口 | 家庭成员、同意范围、计划、记录和资产的家庭范围投影 |
| UI-34 | 家庭档案/长期关系 | **PARTIAL** | 资产/服务读取 | 统一 Journey、服务、权益、记录和家庭可见 Case 的长期档案 |
| UI-35 | 21 天成长营 | **PARTIAL** | 课程内容、今日行动、干预库/Context | 课程日程、完成记录、与 90 天计划衔接及家庭回读 |

## 4. Web 端的同样问题

Web 目前不是独立第二套系统，这一点正确；但默认门户仍以视觉状态机为主体，`runtime=dev-test` 且存在合成 Bearer 会话时才打开多数 API 模式。家庭门户右侧卡片读取了计划、运营回执、审核干预与同意信息，却没有把这些对象真正变成每一个 Web 页面可操作、可回读的家庭场景。下一轮必须让 Web 与 App 订阅同一套家庭体验投影，而不是分别拼装静态卡和局部 fetch。

## 5. 首批不是“补页面”，而是补三个真实公共读模型

### 5.1 `FamilyGrowthExperienceProjection`

以现有 onboarding、growth priority、journey plan、today action、check-in、intervention library 和 consent/context 为输入，按 `tenant_id + family_id` 返回：当前关注、事实输入边界、家长确认后的建议、正在执行的行动、阶段、营日程、下一步。它服务 UI-01、03、04、05、08、09、35 和 Web 家庭门户。

### 5.2 `FamilyServiceCommerceTimelineProjection`

以既有订单意向、权益、预约请求、服务记录、活动兴趣和 `family_operation_followups` 为输入，返回仅限家庭可见字段：已保存、待确认、已处理、下一步、关联服务/权益。它服务 UI-06、14、18、20、21、23、24、30、31、32、34 与 Web 门户。内部负责人、操作备注和 SLA 继续只在运营台可见。

### 5.3 `FamilyAccountProjection`

不另建“我的”模型，而是从家庭成员、同意范围、成长计划、私有记录、服务/商业资产及上面两套投影组装家庭账户。它服务 UI-06、18、29、30、32、33、34，解决当前多处“我的/会员/档案”各自显示不同局部数据的问题。

## 6. 重构优先级与验收

| 批次 | 真实业务纵切 | 覆盖 UI | 最低验收标准 |
|---|---|---|---|
| R1 | 家庭入口→理解→行动→计划→回顾 | 01–05、08–09、35 | 同一家庭今天行动、计划阶段、营进度与已审核建议跨 App/Web 回读；操作持久化、可重试、无结果宣称 |
| R2 | 方案意向→家庭 Case→服务承接→权益资产 | 06、13–24、30–32、34 | 意向/咨询/活动均生成同源家庭可见状态；运营台保留内部字段；外部支付/预约/通知仍 `NOT_EXECUTED` |
| R3 | 私有成长记录→家庭账户→可选传播草稿 | 07、10–12、25–29、33 | 私有记录可保存/回读；发布/分享均是显式草稿/许可；不引入排名、总分或儿童诊断 |

## 7. 立即实施决定

下一步直接从 **R1 的首页聚合投影** 开始：先替换 UI-01 与 Web 家庭门户中的固定任务、固定推荐和局部提示；随后让 UI-04、UI-05、UI-09、UI-35 与同一行动/阶段 readback 联动。这样首先解决用户最直观的“首页像壳”、计划与任务互不相认、App 与 Web 各说各话的问题。
