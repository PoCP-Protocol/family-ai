## 0. 这份文档是什么，不是什么

**这不是新的审计，是既有三份文档的整合。** 本文档不重新做代码级调研，只做三件事：

1. 从 `FAMILY_34_UI_FRONTEND_BACKEND_CONSISTENCY_MATRIX_001.md`（下称"矩阵001"，权威逐页矩阵）里找出当前状态为 `UI_READY_BACKEND_GAP` 或 `GATE_BOUNDARY` 的全部页面；
2. 用 `FAMILY_UI_BACKEND_SCENARIO_CONSISTENCY_AUDIT_V1.md`（下称"场景闭环审计"）和 `notes/ui13-ui14-commerce-gap-assessment.md`（下称"UI-13/14复核"）**纠正**矩阵001里已过时的判断（例如 UI-19/UI-20 已从矩阵001正文表格的 `GATE_BOUNDARY` 升级为矩阵001自己后续新增小节里的 `BACKEND_READY`，UI-13/14 的"缺 DTO"理由已不成立）；
3. 把纠正后的名单按六类闭环分组，逐页给出**结构化决策信息**（工作量量级 / 商业价值层级 / 是否触及宪法边界 / 占位符风险），供项目负责人拍板"补齐"还是"砍掉/保留占位"。

**本文档不给最终结论。** 对 `GATE_BOUNDARY` 类页面，本文档不建议"补后端"（这类页面的问题不是技术缺口，是产品边界决定不做），只帮助负责人判断"这个占位页面要不要留在产品里"。对 `UI_READY_BACKEND_GAP` 类页面，本文档也不直接说"该做/不该做"，只把判断所需的信息摆出来。

来源文档六类闭环划分：项目内未找到 `FAMILY_COMMERCIAL_VALUE_STRATEGY_V2.md`（在当前 worktree 及全部本地分支历史中检索均无此文件），改用矩阵001/场景闭环审计已经在用的六类闭环命名：**ASSESSMENT（评估）/ PLAN（计划）/ GROWTH（成长）/ SERVICE（服务）/ COMMERCE（商业）/ COMMUNITY（社区）**。

价值网络分层参照矩阵001与场景闭环审计的整体判断口径：**层1 = 已验证可跑通并直接支撑收入/留存的核心闭环（评估→方案→任务）；层2 = 支撑层1闭环的服务/商业配套（预约、商城基础设施）；层3 = 锦上添花或尚未被业务证明是刚需的外围功能（积分、社区、名师详情外的边缘页）**。本文档对每页给出层级判断，但最终"层2/层3的边界画在哪"仍是负责人的产品判断，不是技术判断。

### 2.3 GROWTH 闭环 —— 5 个 GATE_BOUNDARY，0 个纯技术GAP

场景闭环审计结论：GROWTH 闭环里 UI-08/UI-11/UI-12/UI-29 全部是 `GATE_BOUNDARY`，"成长效果/榜单/海报/成果均被产品边界限制，不可伪造事实"。矩阵001另有 UI-10 也是 GATE_BOUNDARY。**这 5 页无一是"缺后端"的技术问题，全部是宪法边界决定不做业务事实化。**

| 页面 | 用途 | GATE_BOUNDARY 具体边界 |
|---|---|---|
| UI-08 `growth-report` | 成长报告 | "无独立报告 DTO；不能把静态分值视为事实"——禁止成长评分/诊断/永久标签 |
| UI-10 `growth-child` | 孩子侧成长助手 | "无儿童直接作答/成长结果写入契约"——儿童直接作答继续 HOLD（未成年人高敏感场景） |
| UI-11 `growth-ranking` | 成长榜单 | "不得接跨家庭排名、比较或家庭画像"——永久禁止跨家庭统计/排序 |
| UI-12 `growth-poster` | 成长成果海报 | "无成果事实 DTO；不得生成效果证明"——不得公开分享或成长结果断言 |
| UI-29 `growth-outcomes` | 成长成果/勋章 | "不得把过程指标写成成长效果"——仅家庭自有记录；UI设计审计指出 `BADGES` 是页面内硬编码数组 |

**决策支持信息（GATE_BOUNDARY 页面统一给法，不是"补后端"而是"占位还是砍"）：**

- **不建议的选项：把这些页面接上真实后端事实化数据。** 这会直接撞上宪法第B节"没有Evidence不能形成强判断"、"不做Family Total Score"、"不做家庭Ranking"、CLAUDE.md根级"不做家庭 Ranking"等硬规则，属于 Stop Condition（Coding Constitution E05：需要改变 Consent/Safety 规则）。
- **可选的两条路**（由负责人判断，不是技术判断）：
  1. **保留占位，改为"家庭私有记录回顾"性质**：矩阵001"下一步"栏已给出方向（UI-08"改为支持记录/家庭表达投影并移除事实性分数"；UI-29"改为记录回顾，不输出效果结论"）——这是把页面性质从"效果证明"降级为"个人记录"，仍是技术工作但工作量小（读投影，不需要评分/排名逻辑）。
  2. **从产品里砍掉**：如果负责人判断"成长榜单""效果海报"这类强依赖社交传播/攀比心理的功能与 Family 的宪法定位（不诊断、不打分、不排名）根本冲突，产品叙事上没有替代形态，直接砍掉入口比长期挂一个空占位更干净。
- **占位符风险（若既不补也不砍，维持现状）：高，且是这份清单里风险最高的一组。** UI-11（榜单）、UI-12（海报）这类页面用户预期是"有排名/有可分享的效果证明"，点开却是空态或硬编码假数据（如 UI-29 的 `BADGES`），比普通功能性 GAP 的体验伤害更大——用户会觉得"被骗了"而不是"这个功能还没做完"。UI-10（孩子侧）额外叠加未成年人信任风险。

| 工作量量级 | 中，需要新建合成内容详情投影 | **小，接近"接线"而非"建模型"**——后端 page-objects API 已存在（矩阵001第69-78行记录的 `0023_family_growth_page_objects.sql` 四表+两条API已通过PostgreSQL集成测试），缺的是页面侧调用对接，量级接近矩阵001自己形容的"逐页接入"，是这份清单里工作量最小的几项之一 | GATE_BOUNDARY性质工作量判断见下 | 同左 |
| 商业价值层级 | 层3（社区详情页，非核心闭环） | 层2（服务/家庭档案是SERVICE与用户身份的基础配套，UI-33家庭档案尤其是多处页面依赖的基础数据） | 层3 | 层3 |
| 是否触及宪法边界 | 不触及 | 不触及 | 触及（GATE_BOUNDARY，禁止真实外发/跨家庭推荐——UGC与推荐算法的宪法风险） | 触及（GATE_BOUNDARY，禁止公开画像/等级事实） |

**UI-25/UI-28 GATE_BOUNDARY 决策支持：**

- 不建议的选项：接入真实跨家庭内容流/公开画像——直接撞"禁止真实外发/跨家庭推荐"和"禁止公开画像/等级事实"，这两条不是缺DTO，是产品边界决定不做真实社区功能。
- 两条路：1）矩阵001方向已给出——UI-25做"合成feed read model"（明确非真实用户内容的演示态）、UI-28做"家庭私有记录投影"（不对外，只是个人视角）；2）如果家长社区/社区身份展示当前不是产品核心叙事，直接砍掉入口。
- 占位符风险：高（见上表）。"社区"类页面用户预期强（期待看到别人的内容/评价），空态或假数据的体验伤害在这份清单里数一数二。

**补充：结合"0.1 价值定位与品牌号召"（家是港湾/家庭与家庭的关系）对本节判断的额外考量**

以下是在既有技术/宪法判断（工作量、GATE_BOUNDARY、占位符风险）之外，新增的一层**定位视角**，不替代、不覆盖上面的技术结论：

- 项目负责人在战略文档补充的"0.1 价值定位与品牌号召"一节明确写到，家是港湾、孩子是希望的定位不只指向家庭内部关系，也包括**"家庭与家庭之间的关系"**——原文点名"家庭互助、经验分享（UI-25~28）"是这条定位在产品上的直接承载，并特别提示"这条线现在还不成熟，但不是可以随意砍掉的边缘功能"，取舍需要放在这个定位下重新审视，不能只用"层3暂缓"一句话简单归类掉。
- 逐页核实代码后确认：**UI-25（家长社区 `parent-community`）是这四页里真正对应"家庭互助/经验分享"性质的页面**——它是一个可切换频道（推荐/成长打卡/家长交流/成长案例/同城圈子）、可搜索的经验交流 feed，本质是家长与家长之间浏览、收藏、关注彼此内容的入口。**UI-27（动态详情 `dynamic-detail`）是UI-25 feed条目的详情页，两者是同一条经验分享链路的上下游**，性质相同。
- **UI-28（我的社区 `my-community`）不是同一性质，需要如实区分**：读代码可见它的定位是"我们的家庭内容空间"——私有小记、待发布草稿、我的收藏三个标签页，页面文案明确写着"仅家庭可见""无公开发布""没有粉丝数、公开动态、社区积分或对外可见状态"。UI-28 是**面向自己家庭的个人化视角/私有回看页**，并不承载"家庭与家庭之间"的互动，它只是引用了 UI-25/27 的内容做收藏聚合。把 UI-28 也算进"家庭与家庭关系"的承载范围并不准确——它更接近个人中心，不是社区本身。
- 由此，本节原有的技术/宪法判断（UI-25/28 均为 GATE_BOUNDARY，禁止真实跨家庭内容流/公开画像）**不变**；但对 **UI-25（及其详情页 UI-27）**而言，除了"工作量小/占位符风险高"这层判断，还叠加了一层更重的权重：**如果这条线长期不做或直接砍掉入口，损失的不只是一个具体的社区功能，而是整份战略里"家庭与家庭关系"这个定位在产品上将完全没有承载空间**——目前 34 页里能够对应"家庭与家庭"这一半定位的，只有这一条线。这层考量的性质与"层3锦上添花，可暂缓"不同，不应被这一句话直接盖过，而应该在负责人做取舍时被明确摆出来看到。
- **本文档在此不做进一步引导**：是否要因为这层定位权重而优先投入 UI-25/27，还是维持"技术不成熟、暂缓"的现状判断，甚至直接砍掉——这仍然是负责人需要在"定位的不可替代性"与"当前技术成熟度/工作量/GATE_BOUNDARY合规路径"之间自行权衡的产品判断，本文档不代为拍板。

## 4. 给负责人的三个交叉问题（跨页面共性，值得一次性拍板而非逐页决定）

1. **GROWTH闭环5页（UI-08/10/11/12/29）全部是宪法边界，且场景闭环审计明确指出"全部被产品边界限制"** —— 这不是5个独立的技术选择，是一个产品叙事问题："成长效果如何被用户感知"这件事，Family的宪法立场是不诊断/不打分/不排名。如果这5页长期以当前"原图热点+硬编码占位"的形式存在，等于产品叙事在暗示"有效果证明/有榜单"，与后端能给的"仅家庭私有记录"实际能力持续错位。建议一次性决定这一组的产品叙事方向（记录回顾 vs 直接砍），而不是逐页零散处理。

2. **会员/权益类3页（UI-07/UI-17/UI-30）都卡在"需独立商业化Gate"** —— 这三页的共同瓶颈不是各自的DTO，是"会员权益/积分体系"整体还没有一次独立的商业化立项决策。补齐任何一页之前，更上游的问题是"要不要做会员权益体系"。

3. **UI-13/14的DEV/TEST闭环已完成，但矩阵001文档判断已过时** —— 建议无论对生产化如何决策，都先把矩阵001第30-31行的状态更新为准确表述（UI-13/14复核第36条已给出具体建议），避免后续开发者重复本次"以为要新建DTO"的误判。

4. **COMMUNITY闭环（UI-25/27）的取舍，除了技术成熟度和工作量，是否还要额外权衡它在"家是港湾/家庭与家庭关系"这个战略定位里的不可替代性** —— 战略文档"0.1 价值定位与品牌号召"明确把"家庭与家庭的关系"列为定位的一半，并点名 UI-25~28 是这条定位在产品上的直接承载（本清单核实后确认承载主体具体是 UI-25 及其详情页 UI-27，UI-28 性质是私有个人空间，不完全等同）。如果基于当前技术成熟度判断暂缓这条线，是否需要在产品里保留一个明确的"家长社区·敬请期待"占位入口，而不是完全砍掉入口——以便这个定位承诺在产品叙事上仍然可见，即使功能本身还没上线？这是"暂缓/砍掉"之外的第三种选项，值得和前两条一并纳入决策时的考量范围。
