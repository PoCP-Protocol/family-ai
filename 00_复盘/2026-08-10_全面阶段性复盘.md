## 4. 架构与领域边界评价

### 4.1 做得正确的边界

本阶段最值得保留的是几条边界被代码和测试锁住了:

- `birth_date != LifeStage`: Child 出生日期只是事实,不会自动推断 LifeStage。
- `Relationship != Consent`: PARENT_CHILD / GUARDIAN_CHILD 关系只是资格边界,不会自动授权数据处理。
- `Consent purpose != broad permission`: SERVICE 不等于 MODEL_IMPROVEMENT,RESEARCH 不等于 CONTENT_PUBLICATION。
- `Named Action != arbitrary mutation`: Family Core 核心状态必须通过明确动作改变。
- `Recommendation != Decision != Action`: 当前没有让 AI 或推荐路径直接写核心状态。
- `Perspective != Fact`、`Hypothesis != Fact`: 当前 M1 没有引入主观视角、假设或推断层。

这几条边界对 Family 项目非常关键。项目面向家庭、未成年人、成长干预,一旦把关系、同意、事实、推断、行动混为一谈,后续无论 AI 多强都会变成不可审计系统。

### 4.2 当前设计的保守性是正确的

M1 只做 Family Core,没有抢跑 GrowthProfile、Journey、Intervention、AI、Model Gateway、World Model,这是正确选择。

Family 项目的长期愿景很大,但当前最稀缺的是可信状态基座。先把身份、成员、关系、LifeStage、Consent、Audit、Outbox、Idempotency 做牢,比提前做智能推荐更有价值。

### 4.3 仍需警惕的边界

- TASK-107 Aggregate 只能读 canonical tables,不能成为隐形推断层。
- Consent summary 必须 purpose-specific,不能在响应里形成“全局同意”的表达。
- Family Aggregate 不能包含 GrowthProfile、AI state、Recommendation、Score、Ranking。
- M1 permission 目前是 minimal policy,不能被误写成长期 IAM 方案。
- Python evidence 层不能被 TypeScript 侧用简化 enum 偷偷替代。

## 5. 质量与验证复盘

本阶段质量体系有明显进步:

1. **真实数据库验证成为硬门槛**  
   从 TASK-002R 开始,迁移和 schema 不再只做文本检查,而是必须在真实 PostgreSQL 中执行。

2. **Required tests 不允许 silent skip**  
   早期 DB 测试可能因为缺少 `TEST_DATABASE_URL` 被跳过,后来改为 fail fast,这是正确修复。

3. **并发测试干扰被识别**  
   多个 integration/e2e 文件共享 isolated PostgreSQL test database 时出现并发干扰,通过序列化相关 Vitest 文件执行解决。

4. **Contract checker 经过真实 bug 反馈改进**  
   `CREATE UNIQUE INDEX` 的 DDL-static false negative 暴露后,`tools/validate-contracts.mjs` 被修正。

5. **每个 Named Action 都形成 Gate 报告**  
   这让阶段成果可追溯,也降低了后续 Agent 接手时“只看代码猜状态”的风险。

仍有改进空间:

- 当前大量成果处于未提交状态,版本边界不干净。
- TASK-106 的 Independent CodeReviewer subagent 调用失败后改为 manual review,虽然无 blocker,但独立审查证据弱于原计划。
- 全量测试依赖本地 PostgreSQL `localhost:55433` 约定,后续需要更明确的测试环境 bootstrap 或 CI 策略。
- 目前还没有 TASK-107 级别的 full-flow aggregate gate,所以 M1 不能称为最终完成。

- 不做家庭 Ranking。

这些禁止不是保守主义,而是为了让未成年人数据、家庭关系和成长干预系统保持可审计、可撤回、可解释。

### 裁决 B: 是否先提交当前阶段成果

1. 审阅未提交改动。
2. 确认它们均属于 TASK-101 至 TASK-106 与 Gate 报告范围。

建议 M1 报告后开专项,不要在 TASK-107 内重构。当前 minimal permission 足以支撑 M1,但不能作为长期权限模型。

## 11. 复盘结论

Family 项目本阶段的最大成功,是没有被“智能功能”诱惑而提前越界。项目先建立了可审计的家庭核心状态,并把关系、同意、事实、生命周期阶段这些高风险概念分开处理。这是正确方向。

当前最重要的工程判断是: **不要扩张,先闭环。**

M1 Family Core 距离真正完成只差 TASK-107 的端到端聚合验证和最终报告。完成它之前,项目仍应保持阶段边界: 已完成的是六个写入 Named Action,尚未完成的是完整 Family Core Running。这个诚实边界必须保留。
